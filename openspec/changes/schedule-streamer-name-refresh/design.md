# 名称获取与状态观察解耦

## Context

`MonitorRepository.persistRemoteMetadata` 在观察事务内传入 `remote.name`；详情页的显式刷新与自动补封面也调用 `StreamerRepository.refreshMetadata`。`StreamerDao.updateRemoteMetadata` 防 null 和锁名，不防空白；`NotificationPoster` 对空白回退到「主播」。这不是所有网络错误都会写入「主播」。首次添加还会因 `info?.name == null` 锁住占位值。导入新主播则不会锁名。

0.6 引用的 249.9.1.1 原定昵称缺失时使用配置占位，本变更将占位限定于**没有旧名**时；人工锁仍优先。配置种子是「[待获取]」，不是通知的展示兜底「主播」。不要按字符串黑名单判断：真实昵称也可能就叫「主播」。

## Goals / Non-Goals

名称有独立的获取周期、成功判定和失败记录。直播接口仍可能随状态返回昵称，但不再因此写名称。其他资料沿原路径更新，不新建后台常驻服务，不修改监控 CAS 或为名称刷新申请额外权限。

## Decisions

1. 两个间隔进入 Room 全局配置、修订与读取快照，以正整数小时和分钟录入并校验可安全换算的上限。按每位主播上次完成时间及结果计算到期，而非每隔一天重扫全表；设置变更后重算，不必等待旧周期结束。
2. 复用匿名批量接口及现有批量大小，按 UID 验证原始响应中身份和 `uname.trim()`，与 `liveStatus` 有效性分开。名称消费者不调用监控引擎，不走直播失败计数、状态确认及通知。添加和导入使用已经取得的有效名称初始化成功时间，缺名进入重试而不重复首发请求。详情手动刷新可明确强制单项；补封面不能绕过名称周期。
3. 独立协调器按最近到期时间唤醒；在应用活跃时支持分钟级重试，后台用可延时的一次性工作接续，而非固定一分钟周期 Worker。全量刷新与定时入口共用按 UID 去重的批处理；无目标不排空任务，系统延迟则合并错过的轮次。保存本次开机标识及单调时间、墙钟锚点，跨开机重新计算，调钟不产生密集追赶。
4. 在短 Room 事务中提交名称和本次结果；网络请求不持锁。条件校验 UID、稳定身份、未删除、未人工锁名、请求版本及非维护状态；删除再恢复、备份替换或维护前的返回不能覆盖新状态。名称写入不修改其他观察字段。
5. 业务备份包含两个用户设置，缺字段的旧备份使用默认值；不带在途令牌和设备时钟。恢复、启动及配置变更后重新协调。暂停监控不等于删除主播；手动全量不受首页过滤条件限制。

## Risks / Trade-offs

- 旧库的 `nameLocked=1` 同时可能是人工命名和错误锁住的占位值 → 没有可靠来源证据时保留锁，详情提供显式「恢复跟随远程名称」入口；不按名称等于某种文案批量解锁。
- 设备后台调度可能晚于用户设置 → 界面写明间隔是到期时间，不承诺锁屏或强制停止后准点。分别验收前台计时与恢复行为。

## Migration Plan

在现有 Room v12 上增加显式迁移，保留原名称、锁和部分唯一索引；没有可信刷新时间的未锁记录首次运行即到期。核对新安装种子、配置修订、备份兼容与 `app/schemas`。升级前可导出业务备份，不用卸载重装冒充迁移验证。
