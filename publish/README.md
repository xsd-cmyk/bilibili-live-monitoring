# 主播监控（BiliMonitor）

一个 **Android 本地优先**的 B 站主播开播监控应用：后台定时检查你在监控的主播是否开播，
**如实记录**每一次直播（开播/关播时刻、时长、标题变化、分区变化），并提供历史查询、统计图表、
HTML 报告导出与整应用配置（JSON）备份/恢复；界面外观（名称、图标、主题色、背景图、卡片、底部导航）可自定义。

> 全部业务数据保存在本机 SQLite。除访问 B 站公开接口、以及你自己发起的登录与导入操作外，不上传任何数据。

当前版本：`Kaoru` · `versionName 0622.0` / `versionCode 3`，数据库版本 **10**。

## 功能清单

### 监控

- **双模式后台**：实时模式（前台服务常驻，默认 180 秒一轮）与省电模式（WorkManager 周期任务，15 分钟起）。
- **保活方式可选、可叠加**：前台常驻通知 / 无障碍服务 / **两者同时（双保险）** / 不启用保活；
  界面显示的是**实际**生效状态 —— 选了双保险但无障碍没开时明确提示去开启，而不是假装正常。
- **状态确认策略**：开播/关播都需要连续 N 次观察一致才确认（默认开播 1 次、关播 2 次），避免网络抖动误报。
- **轮播按「未开播」处理**：主播从「直播中」变为「轮播」时，与「未开播」走同一分支 ——
  关闭场次、写入 `END` 事件、触发下播通知；确认沿用下播方向阈值（默认 2 次），
  但**状态仍记为「轮播」**（历史与界面看得出是轮播），在播数也不把轮播算作在播。
- **熔断与盲区**：连续失败按批次计数触发熔断，失败期间如实开一条「监控盲区」，恢复后补检并关闭盲区。
- **单主播独立策略**：检查间隔、开播/关播通知、标题变化通知、分区变化通知、免打扰覆盖。
- **参数真正接线**：检查间隔、单批主播数、并发批次数、批次间隔、请求超时、重试次数、熔断阈值与恢复窗口、
  开播/关播确认次数都可在设置页调整并生效。
- **一键进直播间**：主播二级页直接跳转，**优先唤起哔哩哔哩客户端**（`bilibili://` 深链），
  未安装则落到浏览器；**点通知同样如此**（透明跳板 Activity 逐级降级），并额外保留「查看记录」动作。

### 记录

- **场次**：开播/关播时刻、时长、起止来源与可信度（自动 / 暂定 / 已确认 / 人工修正）。
- **标题变化**：一场直播里改过几次标题全部逐条记录。
- **分区变化**：一场直播里换过几个分区全部记录，历史里显示为 `A → B → C`，导出时呈现为 `A → B`。
- **人工补录与修正**：可手工新增场次、修正时间/标题/分区/备注；修正后的数据带 `CORRECTED` 标记。
- **断档截断**：进程被杀跨越的场次不会写成「时长 = 整个断档」的假场次
  （机制说明见 [`PROJECT_SUMMARY.md`](PROJECT_SUMMARY.md)，逐条取证见缺陷台账）。
- **删除记录**：二级页可删除单条记录（连同事件、标题、分区等子表一起清理）。

### 通知

- 开播 / 关播 / 异常恢复通知，支持**批量聚合**（多个主播同时开播合并成一条）。
- **标题变化**、**分区变化**通知（**默认关闭**，按主播开启；直播中频繁改标题时默认开启等于骚扰）。
- **前台常驻通知内容可自定义**：标题与正文支持 `{count}`（监控中的主播数）与 `{live}`（在播数）占位符，
  设置页带实时预览与「恢复默认」；数量未知时显示 `—` 而不是谎报 0。
- **通知栏「停止监控」**动作：停止服务的同时关闭配置里的监控开关（否则下一个周期会把它拉起来）。
- **免打扰时段**：支持跨午夜；时段内**只抑制通知，场次与历史照常记录**。
- 投递带重试、租约、幂等 `eventKey` 与投递历史；通知历史页可查每条通知的状态。
- **通知点击深链**：`evt:` → 主播详情、`agg:` → 聚合首个主播详情、`problem:` → 健康中心；解析不了则不误跳。

### 历史与统计

- 历史按**开播时间**排序（最新在上），支持按主播/周期/标题关键词筛选、二级页搜索。
- 统计：按日/周/月/年/自定义 + **全部**区间，每位主播独立的场次与时长分布、分桶表。
- 统计结果按数据版本号缓存（快照 + 行级缓存），导出与界面口径一致。

### 导出与备份

- **HTML 报告导出**（历史明细与统计图表两个入口，规则完全一致）：
  - 时间范围：全部 / 按日 / 按周 / 按月 / 按年 / 自定义；
  - 历史明细**按主播分组**，含分区列与可信度列，**选中但无记录的主播也保留空分组**；
  - 统计图表用**内联 SVG 柱状图**（不依赖 CDN，导出文件离线双击可看）；
  - 文件命名：`实际数据区间_主播名_类型.html`（多主播为 `N位主播`，`N` = 选择的主播数；
    类型段为「直播历史」或「统计图表」，因此同一主播的两种导出不会同名）。
- **配置文件（JSON）备份/恢复**：覆盖主播（含标签/分组/单独策略）、直播历史（场次/事件/标题/分区/人工修正）
  与应用设置（监控参数、免打扰、历史容量、导入上限、前台通知文案）；带清单与校验和，
  恢复前有冲突决策页；导入支持系统文件选择器（SAF）读取**任意位置**的文件。
  统计由场次实时算出，不需要单独备份。**刻意不含**登录凭证与和设备绑定的项（保活方式、引导确认）。
- **诊断包**：一键导出运行日志、应用错误、盲区、通知流水线状态、崩溃记录、迁移信息共 6 个 JSON 分片
  （**不含**登录凭证与主播历史明细）。
- **封面保存**：直播间封面可保存到相册（`Pictures/主播监控/`）。
- **数据维护**：容量上限与低水位预警、各表保留策略清理、日志保留策略。

### 外观与交互（可自定义）

| 项 | 能力 |
|---|---|
| 应用名称 | 应用内显示的名称可改（首页标题等） |
| 应用图标 | 上传图片 + **应用内裁剪**（双指缩放 / 拖动）→ 通过系统「固定快捷方式」放到桌面 |
| 主题色 | 调色板 10 色 / **从背景图吸管取色** / 直接填颜色代码（`#RGB`·`#RRGGBB`·`#AARRGGBB`，井号可省） |
| 背景图片 | 选图后作为整页背景，可调**明暗**与**透明度** |
| 卡片外观 | 卡片**透明度**与**明暗**可调（改主题 surface 系列，全应用卡片一起生效） |
| 夜间模式 | 跟随系统（默认）/ 始终浅色 / 始终深色 |
| 底部导航样式 | **Dock 悬浮圆角栏（默认）** / 普通贴底栏 |
| 液态玻璃 | Dock 可开启玻璃效果，参数（模糊半径 / 玻璃浓度 / 高光强度 / 亮边透明度 / 亮边宽度）可自定义；另有「同时应用到所有卡片」开关 |

> **关于图标的能力边界**：Android 不允许第三方应用在运行时替换自己的桌面图标与抽屉图标
> （`AndroidManifest` 是编译期固定的）。能改的是**应用内显示的名称**、**桌面固定快捷方式**的图标与标签、
> 以及通知大图标。应用界面里如实写明了这一点。

### 账号与导入

- **扫码登录**与**用 Cookie 登录**；凭证存于 `EncryptedSharedPreferences`（Android Keystore），
  并通过 `dataExtractionRules` **从云备份与设备迁移中排除**（密文能备份，解它的密钥不能）。
- 从「**按关注导入**」（默认来源）或「直播观看历史」导入主播；数量可自定义（默认上限 500，可改，支持「全部获取」）。
  单页最多 30 条，超过会自动分批翻页并去重；直播观看历史会按直播记录再过滤一层，避免把视频 UP 主当主播导入。
- 导入前有预览弹窗（可搜索、全选/清空），失败或超时有明确原因与「重试」入口。

## 界面与交互特色

### 浮动卡片体系

所有页面顶部标题栏不再是通栏大标题，而是**浮起来的圆角卡片**（自研 `FloatingTopBar`）：
左右 12dp / 上下 8dp 留白、22dp 圆角 + 阴影，颜色取 `surfaceContainer`，因此自动继承外观设置里的
卡片透明度/明暗与玻璃效果。标题**两轴居中**（在整张卡片里居中，而不是在左右按钮夹出的剩余空间里居中），
左右留白按**两侧按钮的实测宽度**动态计算并设上限，按钮多时也不会把标题挤没。

- 首页的搜索框 + 状态/标签/分组筛选收进**一张可收起的浮动卡片**（`HomeFilterCard`），
  收起后仍显示当前筛选摘要；展开状态由 ViewModel 持有，切 Tab 往返后仍保留（进程被杀会回到默认）。
- 历史一级/二级页、统计一级页的搜索栏统一为 `FloatingSearchField`（形状、圆角、内边距一致）；
  统计二级页的粒度/桶值 chips 也整块收进浮动卡片。
- 标签与分组筛选**互斥**（两个归属维度同时约束会产生难以解释的空结果）；「全部 X」固定左侧，其余横向滚动。

### Dock（默认底部导航样式）

- Dock 是**浮在内容之上的浮层**，不是 `Scaffold` 的 `bottomBar` 槽位 —— 因此列表内容能从它**下面滚过去**，
  而不是停在它上方。
- 底部避让高度按 Dock 源码逐项核算为 **136dp**（栏体下沿浮动留白 26 + 栏体 72 + 上沿浮动留白 26 = 124，
  再加 12dp 视觉间隙）；首页按当前导航样式在 136dp / 92dp 之间切换（FAB、消息条与列表末端留白共用同一常量），
  历史与统计一级页的列表底部留白取同一数值 136dp。
- 选中项用主色圆角块标出（与普通样式刻意做得不一样，否则切换看起来像没生效）；
  Dock 自带 `navigationBarsPadding()`，不会被系统导航键压住。

### 液态玻璃

**实现路径**：Compose 没有「采样自己背后内容」的公开 API（`Modifier.blur` 只模糊自己，
`Window.setBackgroundBlurRadius` 是整窗口生效）。因此 Dock 玻璃走的是
Compose UI 1.7 的 `rememberGraphicsLayer()`：每帧把整页内容录进一个图层，
再在全屏画布上按 **Dock 的实测矩形**裁剪、加模糊后绘制 —— 于是 Dock 里透出的是**它下面真实的内容**
（滚动中的卡片等），而不是一张静态壁纸；每帧录制只在「Dock 样式 + 玻璃开启 + 底栏可见」时才挂载。

在实时图层之上再叠三样才有玻璃质感：极淡的体色蒙版、顶部镜面高光、1dp 亮边；五项参数都可自定义。

**能力边界（如实说明）**：

| | 情况 |
|---|---|
| Dock 玻璃 | 折射**它下面的真实内容**（含滚动内容）；没设背景图时也有效 |
| 「同时应用到所有卡片」 | 卡片改为**半透明**（背景壁纸透过卡片显示）。壁纸**是否磨砂由「模糊半径」参数决定**：大于 0 时把壁纸本身模糊，卡片透出的就是磨砂壁纸；**设为 0 则完全不磨砂**，此时卡片只是一层半透明底色（复杂背景上看起来偏淡白）。**卡片不做实时折射** —— 卡片是被录制内容的子孙节点，消费同一图层会触发渲染树自引用（实测 native 崩溃），该方案已回退 |
| 参数共用 | 模糊半径 / 玻璃浓度 / 高光强度 / 亮边两项为 Dock 与卡片共用一组，改一处两边一起变 |

## 安装与构建

环境：JDK 17、Android SDK（`compileSdk 35`、`minSdk 31`）。

```bash
cp local.properties.example local.properties    # 或手写 sdk.dir=<你的 Android SDK 路径>
./gradlew :app:assembleDebug                    # 产物：app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:testDebugUnitTest                # 单元测试（33 个 suite / 315 个用例）
```

### 零安装构建：`管理图标.cmd` + `build-env/`

`管理图标.cmd` 是给非开发者用的图标 / 名称管理器（双击即用、中文交互菜单，最后编译出 APK）。
为了让它在**没装 JDK / Android Studio 的电脑**上也能编译，编译所需的整套工具链可以放进
本文件夹的 `build-env/`（约 1.1 GB）：

```
build-env/
  jdk/                        便携 JDK 17
  android-sdk/                platforms/android-35、build-tools（整份：34.0.0 + 35.0.0）、
                              platform-tools、licenses
  gradle-home/                Gradle 用户目录：发行包本体 + 已下载的依赖（离线编译靠它）
  依赖包说明.txt              来源机器、版本、怎么重新生成
```

- **有它时**：脚本把 `JAVA_HOME` / `ANDROID_HOME` / `GRADLE_USER_HOME` 指向它，并把
  `local.properties` 改写成指向这份 SDK，于是**不联网**（`--offline`）就能编译；
  在菜单里选 0（不联网）即可。实测：把它拷到别处、把 PATH 里本机的 java 去掉，
  仍能 `clean` 后完整编译出 APK。
- **没有它时**：脚本原样使用这台电脑自己装的环境，并在启动时把这一情况说清楚，不会闷着失败。
- **生成它**：在已经装好工具链、并且成功编译过一次的机器上跑
  `powershell -NoProfile -ExecutionPolicy Bypass -File tools\制作依赖包.ps1`
  （增量覆盖，可重复跑；会自动停掉 Gradle 守护进程以免依赖缓存被锁住）。
- **不要把它提交进仓库**：JDK 的 `lib\modules` 单文件就有 122 MB，超过 GitHub 的
  100 MB/文件硬上限，`push` 会被直接拒绝（`.gitignore` 已经排除 `build-env/`）。
  分发请把整个文件夹（或只把 `build-env`）压成 zip 发网盘，或作为 GitHub Release
  的附件（单附件上限 2 GB）。
- **build-tools 为什么要整份打包**：AGP 具体要哪一版是它内部的默认值，工程文件里读不出来
  （本项目实测要 `34.0.0`，而只打"最高版 35.0.0"会在干净机器上报
  `Failed to find Build Tools revision 34.0.0`）。能站得住的推理是：**开发机能编过 ⇒ 它装着的
  这套 build-tools 一定够用**，所以整份拷过去，不猜版本号。
- **摆放检查**：启动时会打印这个文件夹"放对了没有" —— 项目文件是否齐全、依赖包在不在、
  以及这个路径适不适合编译（中文路径、空格、路径过长、云同步目录、网络盘、没有写权限、
  磁盘剩余空间不足，都会给出中文提示）。
- 所有路径都相对于 `管理图标.cmd` 自己所在的文件夹（`%~dp0` / `$PSScriptRoot`），
  整个文件夹可以放在任意位置、整体拷走。

Windows 上还有一键脚本（构建 → 装机 → 启动 → 崩溃/DB 异常自检）：

```powershell
.\build-and-install.ps1              # 需要已连接设备，或已启动模拟器（没有则按脚本内配置自动启动）
.\build-and-install.ps1 -SkipBuild   # 跳过构建，直接安装当前产物
.\build-and-install.ps1 -NoLaunch    # 只装不启动（跳过自检）
```

**`-SkipBuild` 的坑**（脚本行为，值得先知道）：

- 它**只跳过构建**，随后安装的是 `app/build/outputs/apk/debug/app-debug.apk` 这个**当前文件**；
  如果这个文件是上一次构建留下的旧产物，你会装上旧版本却以为验证的是新代码。
  产物不存在时脚本直接报 `APK not found` 退出。
- 脚本里的 SDK 路径、AVD 名称与 AVD 目录是**按作者机器硬编码**的
  （`C:\Users\dd\Android\Sdk`、`BiliMonitor_Test`、`D:\AndroidAvd`），换机器需要先改这三处。
- 构建用 `--offline`：首次构建需要 Gradle 缓存已经预热（否则请先联网跑一次 `gradlew :app:assembleDebug`）。
- 安装用 `adb install -r`（保留应用数据），并在安装后授予通知权限，再启动应用检查
  `FATAL EXCEPTION` / `SQLiteConstraintException` / 迁移异常，出现即失败退出。

**release 构建**开启 R8 混淆与资源压缩（`isMinifyEnabled` + `isShrinkResources`，历史产物约 5.9 MB），
签名材料走 `keystore.properties` 或 `BILIMONITOR_*` 环境变量，缺失时产物为 unsigned。
注意 `checkReleaseBuilds` 为开启状态，`lintVitalAnalyzeRelease` 需要一份体积较大的 lint 依赖：
**离线环境下首次 release 构建会失败（不是代码问题），联网跑一次把依赖拉进缓存即可**。

**仓库内的安装包**：`dist/Kaoru-0622.0-debug.apk`（debug 构建，使用 debug 签名，可直接安装，仅供自测；
未开启混淆与资源压缩，因此体积较大）。

## 技术栈

| 层 | 选型 |
|---|---|
| UI | Jetpack Compose（BOM `2024.12.01` → Compose UI 1.7）+ Material 3 + Navigation Compose |
| 架构 | MVVM（ViewModel + StateFlow）+ 单向数据流；Hilt 依赖注入 |
| 存储 | Room（`DB_VERSION = 8`，迁移链 1→8）+ DataStore（偏好）+ EncryptedSharedPreferences（凭证） |

## 架构要点

完整说明见 [`PROJECT_SUMMARY.md`](PROJECT_SUMMARY.md)。这里只列几条最影响可信度的：

- **单一数据源**：所有业务数据只落 SQLite，界面全部由 Room `Flow` 驱动，没有「内存一份、库里一份」的双写。
- **写入纪律**：一个状态转换 = 一个事务；`observationSequence` + 主播代际 + 全局代际三者同时匹配才允许写入（CAS），
  租约带 **fencing token**，被抢占的旧持有者写入影响 0 行。
- **双时钟**：展示与跨重启用「墙上时间（网络校时）」，租约/窗口/退避用单调时钟，跨开机用 bootId。
- **通知不是直接 post**：先落 `notification_outbox`，由投递器按状态机认领（租约 + 幂等 `eventKey` + 重试）。
- **任何降级都不允许静默发生**：失败要么重试、要么留痕（错误日志 / 健康事件 / 盲区记录），
  界面显示的永远是**实际**状态而不是用户选择所暗示的乐观状态。

## 已知限制与未验证项

> 这一节刻意写得保守：下面这些能力**代码已实现**，但验证程度不同，请按标注理解。

| 项 | 状态 |
|---|---|
| 液态玻璃的实时折射 | Dock 内透出模糊的真实内容曾在设备上以截图确认；此后的坐标修正、幽灵矩形清理与「按需录制」改动只做了**编译 + 装机无崩溃**验证，**滑动时是否实时跟随建议自行确认** |
| 卡片实时折射 | **未做，也不打算按原方案做**：卡片是被录制内容的子孙节点，消费同一图层会造成渲染树自引用（实测崩溃）；现方案是「半透明卡片 + 壁纸磨砂」，而**磨砂程度取决于「模糊半径」参数（设为 0 即不磨砂）** |
| 部分布局观感 | 历史二级页按钮间距、统计二级页 chip 换行等改动只做过编译验证，未逐页在设备上确认 |
| 对话框 | `AlertDialog` 的 text 槽本身不滚动，横屏等极窄条件下内容可能被挤（**已知未修**，彻底修需改对话框结构） |
| 更换背景图 | 机制上已修（引入会变的 `backgroundRevision` 作为解码缓存键），但「已有背景图时直接换图是否立即生效」**未在设备上走完选图流程确认** |
| 轮播按未开播处理 | 单测 90 个全过、编译通过、装机无崩溃；仍需真实主播实测三条：出现下播记录 / 收到下播通知 / 连续 2 次观察到轮播才判定 |
| 自定义图标 | 应用内名称与裁剪预览已验证；`requestPinShortcut` 的系统确认弹窗需要桌面支持固定快捷方式，**未在模拟器验证** |
| 主题色 | 不做深色模式下的对比度校验（由 `onPrimary` 亮度判断兜底）；极亮颜色在深色主题下可能对比不足 |
| 背景明暗/透明度、吸管取色 | 已有纯函数单测覆盖；滑块的连续手势与取色坐标换算未在设备上逐一验证 |
| 一键进直播间 / 通知点击 | 模拟器未装哔哩哔哩客户端，因此**「客户端那一跳成功」未端到端验证**；「未装客户端 → 自动落浏览器」的降级链已实测 |
| 通知大图（封面） | 字段名已用真实响应核实；**通知里的大图是否真正显示需真机确认** |
| 通知清理链 | 顺序与批次无关的清理逻辑已实现，但**存在 30–90 天历史数据时的实际执行路径未跑 instrumented test** |
| Android 12/12L 通知 | 已按 API 等级分支处理权限判定，**未在对应版本的设备上运行验证** |
| 自动化测试覆盖 | 单测 90 个主要覆盖纯函数策略与命名/解析/校验；instrumented 只有 1 个用例（诊断包 6 分片与「不含凭证」边界）。**迁移链、部分唯一索引的约束力、恢复流程的幂等与失败回滚仍是零覆盖区** |
| 主题色/背景图恢复默认 | 「恢复默认外观」会重置名称、图标、主题色、背景图（含明暗/透明度），但**不重置底部导航样式**（刻意：它属于使用习惯） |

其它已知限制：

- 「开播时刻」是**软件确认时刻**，不等于主播真实开播时间（导出文件与界面中均有此说明）。
- 后台监控受系统省电策略影响，任何保活手段都不保证 100% 实时；应用会**如实记录监控盲区**，但不保证不漏。
- 数据库损坏时只做「检测 + 上报」（`PRAGMA quick_check` + 健康事件），不做自动重建 —— 自动重建意味着丢数据。
- 省电模式下通知最快 15 分钟一轮；导出/恢复耗时随场次数量线性增长，超大历史库（十万级场次）需要额外的分批与流式改造。
